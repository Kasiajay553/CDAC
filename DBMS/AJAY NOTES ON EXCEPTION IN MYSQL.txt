Here is a complete, production-ready MySQL stored procedure that incorporates every type of handler (SQLEXCEPTION, NOT FOUND, and SQLWARNING) along with the diagnostic tool (GET DIAGNOSTICS) to catch absolutely everything.
## The Complete "Catch-All" Code

DROP PROCEDURE IF EXISTS highest_lowest_salary;

delimiter // 
create procedure highest_lowest_salary(in empid Int) begin 
    -- 1. Regular variables for logic
    declare emp_salary decimal(10,2);
    
    -- 2. Variables for holding exception/trace information
    declare error_code int;
    declare error_msg varchar(255);
    declare sql_state varchar(5);

    -- =========================================================================
    -- HANDLER 1: THE "NOT FOUND" INTERCEPTOR
    -- Triggers ONLY when a SELECT INTO finds 0 rows.
    -- =========================================================================
    declare exit handler for not found 
    begin 
        select 
            'DATA MISSING' as status,
            1329 as mysql_error_number, -- 1329 is the standard MySQL No Data code
            concat('The emp id you entered (', empid, ') does not exist in the database.') as detailed_error_message; 
    end; 

    -- =========================================================================
    -- HANDLER 2: THE "SQLWARNING" INTERCEPTOR
    -- Triggers for non-fatal issues (e.g., data truncation where MySQL autofixes it).
    -- We use CONTINUE here so the procedure keeps running after logging the warning!
    -- =========================================================================
    declare continue handler for sqlwarning
    begin
        get diagnostics condition 1 
            error_code = mysql_errno, 
            error_msg = message_text,
            sql_state = returned_sqlstate;
            
        select 
            'WARNING DETECTED (Execution Continued)' as status,
            error_code as mysql_error_number,
            error_msg as detailed_error_message,
            sql_state as sql_state_code;
    end;

    -- =========================================================================
    -- HANDLER 3: THE "SQLEXCEPTION" PARENT CLASS CATCH-ALL
    -- Triggers for all severe fatal crashes (misspelled tables, syntax, constraints, duplicates).
    -- =========================================================================
    declare exit handler for sqlexception
    begin
        get diagnostics condition 1 
            error_code = mysql_errno, 
            error_msg = message_text,
            sql_state = returned_sqlstate;
            
        select 
            'FATAL CRASH (Execution Stopped)' as status,
            error_code as mysql_error_number,
            error_msg as detailed_error_message,
            sql_state as sql_state_code;
    end;


    -- =========================================================================
    -- MAIN BUSINESS LOGIC
    -- =========================================================================
    
    -- Line A: Core query fetching employee data
    select salary into emp_salary from employee where emp_id = empid;

    -- Line B: Logical Evaluation
    if emp_salary > 30000 then 
        select 'highest_salary' as salary_level; 
    else 
        select 'lowest_salary' as salary_level; 
    end if; 
    end // 

delimiter ;

## Step-by-Step Breakdown of What Happens for Each Scenario## Case 1: You pass a missing ID (e.g., CALL highest_lowest_salary(9);)

* What happens: Line A executes, looks for ID 9, and finds nothing.
* Who catches it: HANDLER 1 (not found) intercepts it immediately.
* Why SQLEXCEPTION didn't catch it: MySQL treats "no data found" as a data state, not a database crash/exception.
* The Output Grid:

| status | mysql_error_number | detailed_error_message |
|---|---|---|
| DATA MISSING | 1329 | The emp id you entered (9) does not exist in the database. |


## Case 2: The table name is misspelled or missing (e.g., somebody deleted the employee table)

* What happens: Line A tries to access a table that doesn't exist on the server.
* Who catches it: HANDLER 3 (sqlexception) intercepts it.
* How GET DIAGNOSTICS behaves: It works exactly like a Java stack trace. It reaches deep into MySQL's internal system diagnostics, grabs the exact error number (1146), and pulls the raw system message text.
* The Output Grid:

| status | mysql_error_number | detailed_error_message | sql_state_code |
|---|---|---|---|
| FATAL CRASH (Execution Stopped) | 1146 | Table 'your_db.employee' doesn't exist | 42S02 |


## Case 3: The database has corrupted/duplicate IDs (e.g., there are two rows with emp_id = 5)

* What happens: Line A executes. The INTO emp_salary variable is waiting for one value, but MySQL hands it back two distinct numbers. The procedure panics.
* Who catches it: HANDLER 3 (sqlexception) captures it because this is a standard fatal error (Cardinality violation).
* The Output Grid:

| status | mysql_error_number | detailed_error_message | sql_state_code |
|---|---|---|---|
| FATAL CRASH (Execution Stopped) | 1172 | Result consisted of more than one row | 42000 |


## Case 4: Everything goes perfectly right (e.g., emp_id = 1 exists with a salary of $45,000)

* What happens: Line A successfully populates emp_salary with 45000.00. All three handlers remain completely silent. The procedure progresses straight down to the IF statement.
* The Output Grid:

| salary_level |
|---|
| highest_salary |

## Summary Checklist for Handler Behavior

   1. NOT FOUND handles queries returning 0 rows.
   2. SQLWARNING handles mild issues (like data overflow or division by zero under non-strict modes) and keeps running if declared as a CONTINUE HANDLER.
   3. SQLEXCEPTION acts as your Parent Exception class, catching syntax errors, missing schema elements, constraints violations, and multi-row subquery failures.
